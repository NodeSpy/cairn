# E5 + E7: overlayfs over placeholders; reflink / dedupe on btrfs

Run on VM `lfs-b`: Arch, kernel 7.2.11, btrfs on /dev/sdb mounted at `/cache`
(`rw,noatime,discard=async,space_cache=v2`, no compression, 4096-byte block size),
2 vCPU, 3.9 GB RAM. Everything ran as root. Work directory `/cache/exp-ovl/`.

Code and raw output: `experiments/overlay-dedup/`
- `src/main.rs` (`xp` binary: `hsmd` fill daemon, `inw`, `clone`, `clonerange`, `dedupe`, `dedupefile`, `dedupebulk`, `hold`, `lease`, `mmapread`, `sum`, `readall`, `write`)
- `e5.sh`, `e7.sh` (test drivers), `results/*.txt` (raw output)

`xp hsmd` is a small stand-in for the real daemon: `FAN_CLASS_PRE_CONTENT`
group, marks of kind inode / dir (`FAN_EVENT_ON_CHILD`) / mount / sb, 4 worker
threads. On an event it fills the whole file when `st_blocks == 0 && size > 0`,
either by `pwrite` or by `FICLONE` from a store file, then replies `FAN_ALLOW`
(or `FAN_DENY|EIO`). Options choose the event-fd mode (`O_RDWR` / `O_RDONLY`),
whether the write goes through the event fd or through a fresh open of the real
path (`--writevia`), and `--unmark`. Events whose pid is our own are
auto-allowed and logged as `SELFEVT`; this shows nested events and avoids a
self-deadlock.

## E5: overlayfs over placeholders

### Setup
- Overlay `lowerdir=/cache/exp-ovl/e5/lower`, `upperdir`/`workdir` on the same btrfs, plain `mount -t overlay` (no Docker).
- Lower contains placeholders (sparse, right size/mode/mtime, 0 blocks): `small.txt` (20000 B random), `big.bin` (4 MiB), `sub/child.dat` (100000 B), `true` (copy of `/usr/bin/true`, 43320 B).
- Backing content in `/dev/shm/e5store` (tmpfs, so sb/mount marks never see our own reads of it).
- Mark types tried, each a fresh setup per operation: inode (every file under lower), dir (`FAN_EVENT_ON_CHILD` on `lower` and `lower/sub`), mount (`FAN_MARK_MOUNT` on /cache), sb (`FAN_MARK_FILESYSTEM` on /cache).
- Fill via `pwrite` through a freshly opened path fd (see finding 1 for why).
- Full matrix: `results/e5-matrix.txt`.

### Results (read = whole-file read through the overlay mount; correct = bytes equal the store)

| Op through overlay | inode mark | dir mark | mount mark | sb mark |
|---|---|---|---|---|
| read | event, fill, **correct** | same | **no event, zeros** (20000 nonzero=0) | event, fill, correct |
| write (copy-up) | copy-up's read raised event; fill happened; upper copy has real data (7 differing bytes = our write) | same | **no event; upper copy is zeros** (19933 differing bytes), permanent | event + fill, correct |
| mmap read | **no event, zeros** (`nonzero=0`) | same | same, zeros | same, zeros |
| exec `true` | works (rc=0) | works | **rc=126 "cannot execute binary file"** | works |
| stat / ls | no event, size correct, blocks=0 | same | same | same |
| control: direct (non-overlay) read | correct | correct | correct | correct |
| control: direct mmap | event at map time (range 0+file_len), correct | same | same | same |
| control: direct exec | works | works | works | works |

Other observations:
- Events from the overlay arrive with the **real** inode but a path relative to the private layer mount: `path=/small.txt`, not `/cache/exp-ovl/e5/lower/small.txt`. The daemon must key files by inode or file handle, not by the readlink of the event fd.
- Parent-dir mark is one level: `lower` did not cover `lower/sub/child.dat`. With a mark on `sub` too it worked (`dir-child-read`).
- Overlay read produced two events per file (`0+1048576` then `16384+1052672`), the second finding the file filled (`skip-already-filled`).
- mmap through overlay: the process maps, reads zeros, and nothing is logged until a later `read()` raises an event. The mapping is **coherent after a later fill**: a mapping that read zeros showed the real data (changed fnv) after another process's `read()` triggered the fill. So the stale zeros are the page cache state at the time of access, not a permanent copy. Fill-before-mmap is still required for any program that doesn't retry.
- Exec through overlay works because the exec's ELF-header `kernel_read` raises an event (one per read, the first fills the whole file) before any segments are mapped. Later page faults on text pages need no event because the file is already filled. Exec of a placeholder with a mount mark fails with ENOEXEC (zeros).
- Exec with `event_f_flags=O_RDWR` and a write through the event fd works on a direct (non-overlay) path; I saw no ETXTBSY.
- With an **sb mark** the copy-up temp file in the workdir also raises events (`path=/ (deleted)`), and all other /cache I/O (cmp, our own tools) raises events too. Fine for correctness, expensive for throughput. Not measured here (E6).

### Findings that contradict or extend DESIGN

1. **The event fd cannot be opened `O_RDWR` for overlay layer files.** Overlay's layer mounts are read-only private mounts, so `fanotify_read` fails with `EROFS` and the access is denied: the reader gets `EPERM` and exec fails with "Operation not permitted" (`evflags=rdwr` rows in the matrix). §3/§3.1 assume "fill through the event fd". That holds for direct access only. Workarounds tested:
   - event fd `O_RDONLY` and fill through a **new `open(O_WRONLY)` of the real path on the rw /cache mount**. Works.
   - That fd is a normal one, so its `pwrite` or `FICLONE` raises a nested `FAN_PRE_ACCESS` on the same inode, from our own pid. If the thread that holds the pending event is the only one reading the group, this **deadlocks** (tested: `--workers 1` hangs the reader for > 10 s for both pwrite and clone). With >= 2 reader threads and "pid == self => FAN_ALLOW immediately" it works (nested event costs about a microsecond; logged as SELFEVT).
2. **Mount marks do not reach overlay** (confirmed), and failure is silent corruption, including permanent zeros in the upper layer after copy-up. An sb mark does reach it.
3. **mmap through overlay raises no event** (confirmed). Differs from direct access, where `mmap()` itself raises one event covering the whole mapped length.
4. Copy-up **does** trigger a fill (inode, dir, sb marks): good, nothing extra required in that case.
5. Event path is mount-relative (see above).

### Pass/fail (§14.1 criteria)
- Read and write through overlay fill correctly: **PASS** for inode, dir, sb marks. **FAIL** for mount marks.
- mmap through overlay reads zeros: **PASS** (confirmed as expected). Exec of a placeholder works only because exec's header read fires an event.

### What a Docker / overlay integration must guarantee
1. **Fill-before-mount, plus pin.** Every layer file that may be mmapped (executables, shared libs, anything `mmap`ed by a database) must be filled before the overlay is mounted and must stay filled (no eviction, and no truncation or punch) while any overlay that uses the layer is mounted. This is the only rule that makes mmap safe; no mark type helps.
2. Do not rely on mount marks for layers at all. If any placeholder can still be reachable through an overlay, use inode, parent-dir (one level, per directory), or sb marks.
3. If marks are used under overlay, the daemon must (a) use `O_RDONLY` event fds and fill via a normal open of the real path (not the event fd), (b) have at least 2 threads reading the fanotify fd and auto-allow events with `pid == getpid()`, (c) identify files by handle/inode, not event-fd path.
4. Upper dir and workdir must not be under placeholder marks that deny or block (an sb mark makes copy-up temp files raise events; fine if the daemon is up, but a stopped daemon with a mark = blocked containers).
5. A reasonable default: our own snapshotter fills the whole layer (a `FICLONE` from CAS where known), writes it, removes the marks (or never adds them for layers), and only then mounts.

## E7: reflink / dedupe on btrfs

All commands used normal (pre-content-visible) fds unless stated. Raw outputs in `results/e7-*.txt`.

### FICLONE (whole file) and FICLONERANGE

Alignment rules (src S = 16385 B, dst D = 64 KiB unless noted; EINVAL = 22). Block size 4096.

| Case | Result |
|---|---|
| src off, dst off, len all 4096-aligned | OK |
| src_off unaligned (1) | EINVAL |
| dst_off unaligned (1) | EINVAL |
| len 100 or 4097, range does not end at src EOF | EINVAL |
| `len = 0` (to EOF) from an aligned offset, S EOF unaligned, D longer | EINVAL |
| tail incl. unaligned src EOF (12288+4097) into D at 12288 | EINVAL if D longer than the cloned end or D EOF differs (D=20000, 65536); **OK if D size == 16385**, and also OK if D size == 16384 (D grows to 16385) |
| `FICLONE` whole 1 MiB or 100001 B src onto empty or same-size dst | OK, dst takes src size |
| `FICLONE` 100001 B (unaligned) onto an existing **1 MiB** dst | **EINVAL** (dst longer than the cloned end); 1 MiB src onto a 64 KiB dst: OK |
| range past src EOF | EINVAL |
| src_off past src EOF | EINVAL |
| dst offset past dst EOF (aligned) | OK, dst extends |
| self-clone: non-overlapping | OK; overlapping | EINVAL |
| FICLONE onto itself | EINVAL |

Consequence for fills: a placeholder has exactly the src's size, so `FICLONE` works for any size. A mismatch (the file changed size since the placeholder was made) fails with EINVAL; the handler needs a fallback to `pwrite`.

Cost: first clone of a just-written source took **50-75 ms** for 1 MiB (btrfs flushes the source's dirty data); clones of already-synced sources take **50-200 us**. The CAS source must be written, fsynced or old, and a freshly fetched blob clones slowly the first time.

Side effects (1 MiB `FICLONE` to a new file, inotify on the directory):
`OPEN src, CREATE dst, OPEN dst, ACCESS src, MODIFY dst, CLOSE_WRITE dst, CLOSE_NOWRITE src`. So the clone does raise `IN_ACCESS` on the source and `IN_MODIFY` on the destination. dst mtime and ctime change to "now"; src mtime and ctime unchanged. FICLONERANGE into an existing file: same (MODIFY on dst, mtime/ctime of dst change). **Through a fanotify event fd (FMODE_NONOTIFY) the clone is silent**: the reader's inotify saw only its own OPEN, ACCESS, CLOSE_NOWRITE (no MODIFY).

Pre-content events from the clone itself (hsmd `--fill none`, i.e. log and allow; normal fds):

| Marked | FICLONE | FICLONERANGE | FIDEDUPERANGE |
|---|---|---|---|
| dst inode | 1 event on dst, `range=0+0` | 1 event on dst, range=0+len | 1 event on dst, range=0+len |
| src inode | 1 event on src | 1 event on src | **2 events** on src, range=0+len |
| both / dir mark | 1 event each | 1 event each | 2 on src, 1 on dst |

So **clone and dedupe, when issued on a normal fd, do raise `FAN_PRE_ACCESS` on both files**. For a placeholder dst that means the clone triggers the fill handler for itself (handler sees `range=0+0`, treat as the whole file). Cloning onto a marked, still empty placeholder worked (data correct), but only because hsmd allowed the event.

### FIDEDUPERANGE

| Case | Result |
|---|---|
| identical 1 MiB | SAME, 1048576 deduped; both files then show the same physical extent (`shared`) |
| differs by one byte | `status=DIFFERS`, bytes_deduped 0, ioctl errno 0 (status is per-dest) |
| differing byte lies outside the requested range | SAME for the requested range |
| odd size 100001 B, len = file size (EOF tail) | SAME, 100001 (works with dst `O_RDONLY` and `O_RDWR`) |
| off 100, len 4096 | per-dest status EINVAL |
| len 4097 mid-file | SAME, 4097 (but the pair already shared extents, so not conclusive) |
| src == dst same range | EINVAL; different range, different content: DIFFERS |
| dst range beyond dst EOF | EINVAL |
| dst already shares the extent | SAME, 142 ms (it still reads and compares; no short-circuit) |
| 1000-byte (inline extent) files | status SAME, but **no space reclaimed**: 10k x 1 KiB files, fs used 479657984 -> 479723520 (-64 KiB in the wrong direction). Inline extents can't be shared. |
| dedupe, dst fd `O_RDONLY` as root | works (owner or write permission suffices) |

Timestamps and inotify: dedupe changes **neither mtime nor ctime of src or dst**, and raises **no inotify events** other than the OPEN / CLOSE_NOWRITE (or CLOSE_WRITE when we open dst `O_RDWR`) of the opens we made ourselves. No ACCESS, MODIFY or ATTRIB. (So no git rehash, no remote-change false positives. The only thing visible is our own opens, which the FID group sees as OPEN.)

Concurrent users of the dst (3 s each; second dedupe issued with an `O_RDWR` fd while held):

| dst held by another process as | dedupe result |
|---|---|
| open O_RDONLY | SAME, content intact |
| open O_WRONLY (idle) | SAME |
| `mmap` PROT_READ MAP_SHARED | SAME, mapping content unchanged before/after (same fnv) |
| `mmap` PROT_READ\|PROT_WRITE MAP_SHARED | SAME, mapping unchanged |
| a writer rewriting byte 0 in a loop for 2 s, 200 dedupes of the rest | 200 x SAME, no errors, no DIFFERS |

Never ETXTBSY / EBUSY. Extents were shared afterwards in all cases.

Lease interaction (holder takes `F_RDLCK` on dst; `LEASE_INTACT` printed `F_GETLEASE=0` = F_RDLCK still held):

| Action | Lease |
|---|---|
| dedupe with dst opened `O_RDONLY` | **not broken** (extents replaced underneath it) |
| dedupe with dst opened `O_RDWR` | broken, by the **open** (2 ms, holder released at once) |
| dedupe with a lease held on the **src** | not broken |
| `FICLONE` onto a leased dst | broken by the write-open, then the clone ran |

So a dedupe that goes through a read-only fd is invisible to the lease gate; any write-open (including the one `FICLONE` needs) breaks the lease as usual.

Space reclaimed (`btrfs filesystem usage` used-bytes, `compsize`, `btrfs filesystem du`):
- 3 x 256 MiB identical files written separately: used +769 MiB; `compsize` Disk Usage 805306368 (6 extents, 0 refs shared); `fi du` Exclusive 768 MiB.
- After deduping 2 of them against the third (32 calls): used reclaimed **513 MiB**; `compsize`: Disk Usage 268435456, Referenced 805306368, 2 extents (34 refs); `fi du`: Exclusive 0, Set shared 256 MiB.
- Partial overlap (file = first 128 MiB of A + 128 MiB new): chunked dedupe of the first 128 MiB reclaimed **128 MiB**, the rest untouched (as expected `dedupefile` stops at the first DIFFERS chunk; granularity per call).
- 10240 x 16 KiB identical-pair files: reclaimed 161 MiB of 160 MiB (accounting noise).
- 1 GiB x 4 identical: reclaimed 3078 MiB (3 duplicates), btrfs free space updated after a `btrfs filesystem sync` and about 3 s.

Throughput:

| Workload | Result |
|---|---|
| 10240 x 16 KiB, **cold** cache | 86.2 s, 119 files/s, 8.2 ms per ioctl |
| same files, warm / already shared | 0.276 s, 37 037 files/s, 16 us per ioctl |
| 10000 x 4 KiB, cold | 18.2 s, 549 files/s, 1.7 ms per ioctl |
| 10000 x 1 KiB (inline), warm | 0.226 s, 44 307 files/s, 12 us (no actual dedupe) |
| 256 MiB x 2 files, 16 MiB chunks, warm | 0.033 s = 7.8 GiB/s |
| 1 GiB, **single call**, warm | 164 ms (6.2 GiB/s), `bytes_deduped` = full 1 GiB in one call |
| 1 GiB, 16 MiB chunks (64 calls), warm | 0.165 s (6.2 GiB/s) |
| 1 GiB, 128 MiB chunks (8 calls), warm (2 GiB working set) | 0.156 s (6.6 GiB/s) |
| 1 GiB, single call, **cold** | **851.7 s (1.2 MiB/s)** |
| same 2 GiB pre-read with `cat`, cold | 21.8 s (about 94 MiB/s) |

The kernel imposes no 16 MiB cap on the caller; one ioctl deduped all 1 GiB. A first 128 MiB-chunk run took 307 s because the 4 GiB working set exceeded 3.9 GB RAM and evicted `big`; the clean rerun (2 GiB) is the number above. Sequential cold read speed of this disk is 172 MB/s (`dd`), so **cold dedupe is about 100x slower than disk speed: the kernel reads both files page by page with no readahead, so it is latency bound.** (The 10k-file cold case behaves the same.)

### Reflink from CAS into a placeholder, inside the pre-content handler (fill path)

Setup: 1 MiB placeholder, inode mark, store blob on the same btrfs (never marked), hsmd `--fill clone` or `pwrite`.

| Config | Result |
|---|---|
| clone via event fd (`O_RDWR`, direct file) | **correct, 103 us handler, no nested event, no inotify MODIFY** |
| clone via fresh path fd, 4 workers | correct, 104 us, **1 nested SELFEVT** (auto-allowed) |
| clone via fresh path fd, 1 worker | **deadlock** (reader hung > 10 s, nothing filled) |
| pwrite via fresh path fd, 1 worker | **deadlock** |
| pwrite via event fd | correct, silent |

Effect on metadata: after either fill, mtime becomes the fill time (we set it to 2020-01-02 first), ctime also the fill time, `blocks` goes 0 to 2048. The handler must `futimens` the original mtime back (emits `IN_ATTRIB`, §3.1). After a clone fill the placeholder shares its extents with the store blob (`shared`), so a clone fill uses no extra space (fs used after the 1 GiB clone fill was 1491599360 B, the same as the store alone).

Speed, handler time (`EVT us=`) with `--unmark`, 4 worker threads, event-fd write; store blobs warm in the page cache:

| Size | pwrite handler | clone handler |
|---|---|---|
| 1 file x 1 GiB | 25.5 s | 0.11 ms |
| 1000 x 1 MiB | 31.6 ms avg | 77 us avg |
| 10000 x 16 KiB (cold store) | 2.25 ms avg | 103 us |
| 20 x 64 MiB (cold store) | 2243 ms avg | 92 us |
| 1 x 1 GiB (cold store) | 35.1 s | 137 us |

Whole-run reader times (reading every placeholder after the fill; cold page cache for the placeholder, so reads of clone-filled files hit disk): 10000 x 16 KiB: pwrite 24.0 s vs clone 12.7 s; 1000 x 1 MiB: 43.8 s vs 18.8 s; 20 x 64 MiB: 45.0 s vs 14.6 s; 1 GiB: 35.2 s vs 12.7 s. The `pwrite` times here are dominated by this VM's write throughput (about 30-40 MiB/s buffered, throttled by dirty-page limits), which a real fetch from the NAS would also pay once.

Caveat: this compares copy from a **locally present** blob. A clone only avoids writing when the content is already in the local CAS; for the first fetch from the network there is nothing to reflink and `pwrite` is needed.

## Pass/fail summary

| ID | Criterion | Verdict |
|---|---|---|
| E5 | read and write through overlay fill correctly | PASS with inode/dir/sb marks and a fill via normal path fd (+ self-event handling); **FAIL with mount mark** (silent zeros, zeros copied up) and **FAIL with `O_RDWR` event fd** (EROFS -> EPERM) |
| E5 | mmap through overlay reads zeros | PASS (confirmed: no event, zeros) |
| E7 | `FICLONE` / `FIDEDUPERANGE` behaviour, events, ctime effects | PASS, characterised above. Clone: ACCESS(src) + MODIFY(dst), dst mtime/ctime change. Dedupe: no inotify, no mtime/ctime change, no lease break. Both raise pre-content on src and dst when issued on normal fds |
| E7 | reflink fill viable inside the handler | PASS via the event fd (silent, 100 us); via a path fd it needs a multi-thread self-allow design |

## Design changes needed

1. **§3.1 overlayfs row**: correct and extend:
   - mmap through overlay fires nothing (confirmed), read/write/copy-up fire on the real inode (confirmed), mount marks don't reach (confirmed), sb marks do (confirmed).
   - **Event fd of an overlay layer file cannot be `O_RDWR`** (EROFS, access denied). The fill must go through a new `open(O_WRONLY)` of the real path, which raises a nested event.
   - Event path is relative to the layer mount; key by file handle.
2. **§3 / hydrate handler**: when a group may see events for its own writes (path-fd fills, dedupe/clone by the daemon on marked files), run >= 2 reader threads and auto-allow events whose pid is ours, or remove the mark first. A single-threaded reader deadlocks (tested). Also applies to any daemon-issued `FIDEDUPERANGE` / `FICLONE` on a still-marked file.
3. **§9 hydration by FICLONE**: confirmed, adopt it, with:
   - do it through the event fd (silent, no nested event);
   - require dst size == blob size (placeholders do), otherwise (or on EINVAL / cross-device) fall back to `pwrite`;
   - restore mtime after (clone changes mtime/ctime, `IN_ATTRIB` fires);
   - make CAS blobs synced before first use (first clone of a freshly written blob took 50-75 ms because btrfs flushes the source);
   - the filled file shares extents with the blob (no space cost).
4. **§9 client dedupe**: confirmed to be silent (no inotify, no mtime/ctime, no lease break, works under open readers, writers and mmaps without errors), so it can run after the lease is taken. Add:
   - **do it while the file is still in the page cache** (right after hashing), or pre-read both with `readahead`/`posix_fadvise(WILLNEED)`. Cold dedupe ran at 1.2 MiB/s (about 100x below disk speed); warm ran at about 6 GiB/s. Background cold dedupe over many files is not viable without prefetch.
   - skip files whose extents are inline (< about 2 KiB): the ioctl reports SAME but nothing is freed.
   - offsets must be 4096-aligned; length unaligned only for the EOF tail.
   - DIFFERS is per-dest status (ioctl returns 0); handle it as "not identical" without error.
   - the dedupe on a marked file or placeholder raises 1-2 pre-content events from our own pid; same rule as item 2.
5. **§11 Docker**: keep "fill before mount, pin while mounted" as a hard requirement, and note why it is required rather than optional: mmap never raises an event (zeros) and, with the mount mark option, a copy-up persists zeros. Our snapshotter should not rely on marks at all for layers.
6. **§14.1 E5 criteria**: add "mount-mark: expect FAIL (documented)" and "exec of a placeholder through overlay works only via the header read" as explicit results. Consider adding E5b: run with an actual Docker/containerd on the VM (not done here; plain overlayfs mount was used, as allowed).

## Not done / limits
- No real Docker run (plain `mount -t overlay`).
- Tests ran as root; the unprivileged-dedupe-permission case (non-owner, no write permission -> EPERM) was not tested.
- One VM, one btrfs, one subvolume; no cross-subvolume or cross-filesystem clone (EXDEV) test.
- The cold-cache and bandwidth numbers are specific to this VM's disk (about 172 MB/s sequential read, tens of MB/s sustained buffered writes).
- Unmarked-count/mark-memory costs (E6/E9) were not measured; 10000 inode marks were set in 0.4-0.5 s.
