# E9 — scale: what the design costs at 100k / 1M / 3M entries

Date 2026-11-12. Code: `experiments/scale/` (`src/main.rs`, `run.sh`). Raw logs: `docs/experiments/E9-data/results/{100000,1000000,3000000}/`.

## Setup and caveats

- VM `lfs-srv`: kernel 7.2.11, **2 vCPU, 3.9 GiB RAM**, 512 MiB swap, 20 GiB btrfs on `/cache` (plain directory, default mount options). Static musl binary, run as root.
- Tree shape: synthetic code-checkout. the target monorepo does not exist on the devbox, so sizes are lognormal (median 4 KiB, sigma 2.0, i.e. p90 ≈ 52 KiB, p99 ≈ 410 KiB, p99.9 ≈ 1.7 MB, max 5–24 MB). Fan-out averages 15.0 (files and subdirs together). Dir depth reaches only **6 / 7 / 8** (avg 4.3 / 5.5 / 6.0), not 10. Every file is a sparse placeholder (`set_len` plus mtime via `futimens`); no data blocks.
- "Entries" = files + dirs, so the nominal scales are 99,721 / 999,841 / 2,991,684 actual entries (93,055 / 933,175 / 2,791,684 files).
- Memory is measured in-process from `/proc/meminfo` and `/proc/slabinfo` after `sync; drop_caches=3` (so "pinned" = still held after dropping caches). A guard stops a phase when `MemFree` < 220 MiB. `MemAvailable` is useless here: it counts pinned inode slabs as reclaimable (e.g. at 1.67M inode marks `MemAvailable` fell 484 MiB while `MemFree` fell 2 GiB).
- The test disk is shared and its latency varied a lot (observed ≈ 26 ms per read at ~30 IOPS during the 3M runs). Cold numbers, and the 3M numbers in general, are noisy. The 3M `leases` and `fid` stages ran cold (the `WARM=1` prewarm was stripped by `sudo`); this only affects timings, not memory.
- fanotify/lease behaviour is from one kernel (7.2.11). Slab aliasing in `slabinfo` renames some caches (`fanotify_mark` shows as `sigqueue`, 80 B; `file_lock_ctx`/`fasync_cache` show as `ftrace_event_field`/`ip_fib_trie`).

## 1. Materializing placeholders

| | 100k | 1M | 3M |
|---|---|---|---|
| entries (files / dirs) | 99,721 (93,055 / 6,666) | 999,841 (933,175 / 66,666) | 2,991,684 (2,791,684 / 200,000) |
| logical bytes | 2.8 GB | 28.1 GB | 84.2 GB |
| create time (mkdir + file create, 2 threads) | 1.6 s | 18.4 s | 194.5 s |
| `sync` afterwards | 6.0 s | 38.6 s | 55.4 s |
| entries/s (create only) | 62k | 54k | 15k |
| btrfs metadata used (`btrfs fi df`, DUP) | 37.6 MiB | 376 MiB | 1.47 GiB |
| metadata per entry | ≈ 395 B | ≈ 394 B | ≈ 515 B |
| on-disk metadata (×2 DUP) | 75 MiB | 752 MiB | 2.9 GiB |
| data used | 5 MiB | 5 MiB | 5 MiB |
| inode count | btrfs has no fixed inode table (`df -i` shows 0); count = entries | | |

The 3M rate drop (54k/s to 15k/s) comes from dirty-metadata writeback and metadata cache pressure on 4 GiB RAM plus the slow shared disk. The metadata tree (1.47 GiB at 3M) no longer fits in RAM alongside the inode cache, which is what makes everything else at 3M slow.

## 2. fanotify `FAN_PRE_ACCESS` marks

Default `fs.fanotify.max_user_marks` = **35,997**. A normal group fails with `ENOSPC` at exactly 35,997 marks (tested at 100k). Everything below uses `FAN_UNLIMITED_MARKS` (needs `CAP_SYS_ADMIN`).

| Mark strategy | metric | 100k | 1M | 3M |
|---|---|---|---|---|
| **inode mark on every file** | marks added | 93,055 | 933,175 | **1,667,072 of 2,791,684 (stopped by memory guard)** |
| | `fanotify_mark` syscall time | 1.8 s (51k/s) | 23.5 s (40k/s) | 141 s (11.8k/s, under reclaim pressure) |
| | Slab delta, live | 120 MiB | 1,266 MiB | 2,284 MiB |
| | **Slab delta, after `drop_caches` (pinned)** | 103 MiB | 1,071 MiB | 1,926 MiB |
| | of which SUnreclaim | 13 MiB | 145 MiB | 259 MiB |
| | per marked file (pinned) | 1.17 KB | 1.20 KB | 1.21 KB |
| **dir mark** (`FAN_EVENT_ON_CHILD`) on every dir | marks | 6,666 | 66,666 | 200,000 |
| | syscall time | 0.95 s (7.0k/s) | 11.3 s (5.9k/s) | 37.2 s (5.4k/s) |
| | Slab pinned after drop | ≈ 3 MiB | 68 MiB | 211 MiB |
| | per marked dir (pinned) | ≈ 1.1 KB | 1.07 KB | 1.11 KB |
| **one sb mark** (`FAN_MARK_FILESYSTEM`) | marks / time / memory | 1 / 0.01 s / ≈ 0 | same | same |

Where the per-mark bytes go (inode marks): `btrfs_inode` ≈ 1,010 B and `dentry` ≈ 205 B per file, both **pinned by the mark** (an inode with a mark cannot be evicted), plus `fanotify_mark` 80 B and `fsnotify_inode_mark_connector` 40 B. So the mark itself is only 120 B; the cost is that the whole placeholder namespace stays resident in the inode cache. Everything returns to baseline when the group fd is closed.

The same namespace scanned without marks costs the same ≈ 1.2 KB/entry in `btrfs_inode`+`dentry`, but that memory is reclaimable and is evicted under pressure; marks make it permanent.

## 3. Read leases on N files

`RLIMIT_NOFILE` was raised to N+4096 as root (hard limit here 524,288; `fs.nr_open` = 2,147,483,584; `fs.file-max` = LONG_MAX). No fd limit was hit. Opening and leasing stopped at 1,560,576 files at the memory guard on the 3M tree.

| | 100k | 1M | 3M tree |
|---|---|---|---|
| files opened + leased | 93,055 | 933,175 | **1,560,576 (memory guard)** |
| `F_SETLEASE F_RDLCK` time (all) | 0.11–0.14 s (≈ 700–840k/s) | 1.4 s (668k/s) | 1.83 s (855k/s) |
| release leases + close fds | 0.22–0.28 s | 2.2 s | 3.3 s |
| open-only Slab delta (pinned) | 129 MiB (1.45 KB/file) | 1,346 MiB (1.51 KB) | 2,267 MiB (1.52 KB) |
| lease increment Slab (all SUnreclaim) | 30 MiB (342 B/file) | 305 MiB (343 B) | 511 MiB (343 B) |
| **total per leased file** | **1.80 KB** (0.61 KB unreclaimable) | 1.86 KB | 1.87 KB |
| total (live) | 159 MiB | 1,652 MiB | 2,778 MiB (unreclaimable 912 MiB) |

Per-file breakdown: `btrfs_inode` 1,008 B + `dentry` 203 B (pinned by the open file), `struct file` (`filp`) 192 B + LSM blob ≈ 66 B × 2, `file_lease` 160 B + `file_lock_context` 56 B + `fasync` 48 B + one 64 B alloc = 343 B. Taking leases is cheap and linear (no slowdown across chunks); memory is the limit. Time to open files (walk + `open`) dominates: 1M files in ≈ 51 s with a warm-ish tree; 300k cold files took 175 s on the slow disk.

**Lease-break signal loss (important).** With leases held on 93k–200k files, we triggered a break on every one (non-blocking write-open → `EWOULDBLOCK`, signal sent via `F_SETSIG` to an RT signal read from a signalfd):

| `RLIMIT_SIGPENDING` | breaks | RT signals delivered | SIGIO fallbacks |
|---|---|---|---|
| default (15,382) | 93,055 / 200,000 | **15,382** (all other breaks silently lost) | 1 (carries no fd) |
| raised to 4,000,000 | 93,055 / 200,000 | all (93,055 / 200,000, all unique fds) | 0 |

So a `git checkout` or build that opens more than ~15k leased files for writing within one drain interval loses lease-break notifications; the writers proceed after the lease-break timeout (45 s) with the daemon unaware. Raising the rlimit fixes it (the daemon runs as root), and `CLOSE_WRITE` events from the FID group are a backstop. Trigger rate was ≈ 150–270k breaks/s.

Where per-file leases become impractical: not at fd or CPU limits but at memory. With ~1.9 KB per leased file, 1M leases cost ≈ 1.9 GB (of which ≈ 0.6 GB unreclaimable), and ≈ 1.6M leases exhaust a 4 GiB machine. A cache covering a monorepo-sized namespace (≥ 1M files) should not keep every filled file leased.

## 4. FID notification group (`FAN_REPORT_DFID_NAME`, CREATE/DELETE/RENAME/CLOSE_WRITE/OPEN, `FAN_ONDIR`)

Workload: create then unlink 100,000 empty files spread over 1,000 directories, with the reader thread in the same process on a 2-vCPU VM (so reader and writer compete for CPU).

| | 100k tree | 1M tree | 3M tree |
|---|---|---|---|
| dir marks: count / time | 6,666 / 1.9 s | 66,666 / 16.6 s | 200,000 / 42.5 s |
| dir marks: pinned memory after drop | 4 MiB | 68 MiB | 213 MiB |
| baseline create / delete (no group) | 1.6 s / 2.4 s | 2.1 s / 3.0 s | 2.0 s / 1.9 s |
| with dir marks, fast reader: create / delete | 2.2 s / 2.5 s | 3.8 s / 3.0 s | 2.9 s / 2.2 s |
| with **sb mark**, fast reader: create / delete | 2.1 s / 2.5 s | 4.4 s / 3.1 s | 2.8 s / 2.2 s |
| events delivered (100k files) | 201k | 201k | 201k |
| overall rate | 35–39k events/s | 16–21k/s | 23–24k/s |

Each created file generates CREATE, OPEN and CLOSE_WRITE; the kernel merges them, so 100k create+delete = ≈ 201k delivered events (one per create, one per delete, plus 1k directory OPENs). With a fast reader the reader keeps up (queue drained 0.00–0.10 s after the workload ended); the rate is workload-bound. Cost to the workload is about +30 to +100 % on create and ≈ 0 to +15 % on delete, similar for dir and sb marks (differences between the two are within the run-to-run noise on this VM).

Queue behaviour with a slow reader (reads nothing until the workload ends):

| queue | events kept | overflow | memory |
|---|---|---|---|
| `FAN_UNLIMITED_QUEUE` | all 201k | no | +20 MiB SUnreclaim (`kmalloc-cg-96`, ≈ 100 B/event) |
| default (16,384) | **16,385 of 201k (8 %)** | `FAN_Q_OVERFLOW` once; everything after is lost | ≈ 1 MiB |

A default-queue group overflows after 16k events in a burst (a 100k-file checkout or delete), which forces the DESIGN §7.4 rescan (see §5 for its cost). Use `FAN_UNLIMITED_QUEUE` and a dedicated fast reader, with a cap on queue depth enforced by the daemon.

## 5. Startup scan (walk + lstat of every entry, `read_dir` + `DirEntry::metadata`)

`drop_caches` before the cold pass; j = worker threads (shared directory stack).

| | 100k | 1M | 3M |
|---|---|---|---|
| cold, j=1 | 3.9 s (26k/s) | 41.4 s (24k/s) | 218 s (14k/s) |
| warm, j=1 | 0.32 s (313k/s) | 3.6 s (280k/s) | **352 s (8.5k/s)**, then 33.7 s on the next pass |
| cold, j=2 | 1.6 s (62k/s) | 20.6 s (49k/s) | 69 s (43k/s) |
| warm, j=2 | 0.19–0.22 s (450–520k/s) | 2.8–3.1 s (324–357k/s) | 22.7–23.7 s (126–132k/s) |
| slab left after warm scan | 108 MiB | 1,151 MiB | 2,393 MiB |
| per entry | 1.15 KB | 1.21 KB | 0.84 KB (cache thrashing) |

At 3M the "warm" single-thread pass was slower than the cold one: btrfs metadata (1.47 GiB) plus inode/dentry cache no longer fit in 3.9 GiB, so the pass evicted what it needed (and the disk was slow). The scan is I/O-latency-bound when cold, so more threads help almost linearly (`j=2` ≈ 2–3× at 3M); a 4–8-thread scan or directory-order prefetching would help further. A recovery scan of 1M entries costs 20–40 s cold and 3 s warm; at 3M it costs about a minute with 2 threads on a RAM-constrained box.

## Where it breaks (summary)

| Limit | Where | Notes |
|---|---|---|
| `fs.fanotify.max_user_marks` = 35,997 | at 36k inode marks | needs `FAN_UNLIMITED_MARKS` or a sysctl bump |
| RAM: inode marks pin inodes | ≈ 1.2 KB/file, 1.67M files on 3.9 GiB (guard hit, real OOM close) | 1M marked placeholders = 1.1 GiB pinned; 3M ≈ 3.4 GiB |
| RAM: per-file lease + open fd | ≈ 1.9 KB/file, 1.56M files on 3.9 GiB | 1M leases = 1.9 GiB |
| `RLIMIT_SIGPENDING` 15,382 | at 15k simultaneous lease breaks | silent loss of breaks; raise rlimit |
| default fanotify queue 16,384 | at 16k events in a burst | overflow, then full rescan |
| scan time cold | 1M: 21–41 s; 3M: 70–220 s | warm cache does not fit at 3M on 4 GiB |
| materialize | 3M: ≈ 3.2 min + 55 s sync | btrfs metadata ≈ 0.4–0.5 KB/entry (1.5 GiB at 3M, ×2 DUP) |
| fd limits | not reached | `nr_open` 2^31, `file-max` unlimited; only `RLIMIT_NOFILE` needs raising |

## Extra check: ignore masks work with pre-content marks

Because a mark-per-file does not scale, we tested whether a broad mark can be combined with per-inode exceptions. On this kernel, a `FAN_PRE_ACCESS` mark on the sb (or on a dir with `FAN_EVENT_ON_CHILD`) plus `fanotify_mark(FAN_MARK_ADD | FAN_MARK_IGNORE | FAN_MARK_IGNORED_SURV_MODIFY, FAN_PRE_ACCESS)` on one file in that scope:

- the ignored file produces **0** pre-access events on read, on write, and on read after write (the ignore survives modification);
- the unignored sibling produces 1 event per read.

Both sb and dir scopes behave the same (`E9-data` has no log; run `scale ignore <dir> sb|dir`). Not tested: removing the ignore mask while a file is open, ignore masks on a mount-mark scope, and per-event cost for un-ignored filled files (that is E6).

## Design changes needed

1. **Do not put a `FAN_PRE_ACCESS` inode mark on every placeholder.** At 1M files it pins ≈ 1.1 GiB of unreclaimable inode cache, at 36k it hits the default limit, at ~1.7M it exhausts a 4 GiB box, and each add costs ≈ 25–80 µs. Replace with **one sb mark** (or a mount mark on a dedicated bind mount, untested here; the cache lives on its own btrfs, so sb is simplest). One mark, no memory, no limits. The daemon's handler looks up the inode in its state table and answers `FAN_ALLOW` immediately for non-placeholders. Dir marks are the worse middle ground: 66k–200k marks pin ≈ 70–210 MiB, take 11–42 s to install, and still deliver an event for every child open.
2. **Use ignore masks for hot filled files.** Once a file is filled and leased, add `FAN_MARK_IGNORE | FAN_MARK_IGNORED_SURV_MODIFY` on its inode, so reads of hot files cause zero events (this replaces "remove the mark once filled", which assumed per-file marks). Eviction order stays: remove the ignore mask first (the file is again visible to the sb mark), then upgrade the lease. Verify (E6b) the cost of an `ALLOW` round trip for filled files that are not hot, since every read/write of a cold filled file will cost one event; this decides how large the hot set must be.
3. **Lease strategy: a bounded hot set, not all filled files.** Budget ≈ 2 KB per leased file (lease 343 B + file 192 B + pinned inode/dentry 1.2 KB). Keep a cap (suggest 100k–250k files, ≈ 200–500 MiB, configurable, derived from RAM) of leased+ignored files chosen by LRU on OPEN events (the FID group already feeds this) and by recent writes/fills. Demoting a file means: drop lease, close fd, remove ignore mask; it then becomes "filled, cold", gated by the sb-mark event path. For cold filled files the pre-content handler decides: open O_RDONLY, try `F_RDLCK` (E3 writer test); `EAGAIN` = a writer is open, so get the server lease before `ALLOW`; success = no writer, drop and `ALLOW`. This gives write gating for the whole namespace with O(hot set) kernel state.
4. **FID group: one sb mark, not per-dir marks.** Event throughput and overhead are the same for dir and sb marks, but dir marks cost 66k–200k marks, 70–210 MiB pinned, and 17–43 s to install (plus a mark per new directory forever). The daemon must filter events to its cache root (ensure `/cache` is a dedicated filesystem, or resolve handles and discard foreign ones).
5. **FID queue: `FAN_UNLIMITED_QUEUE`, a dedicated high-priority reader, and a depth cap.** The default 16,384 queue loses 92 % of a 100k-file burst. On overflow, rescan only the dirs affected if known; otherwise the full scan (§5 numbers).
6. **Raise `RLIMIT_SIGPENDING`** (and `RLIMIT_NOFILE` to at least hot-set size + headroom) at daemon start, or use a different lease-break path. On any `SIGIO` fallback (no fd) treat it as "lost breaks": rescan the leased set (try `F_RDLCK`/`F_GETLEASE` on each) and rely on `CLOSE_WRITE` events as the backstop.
7. **Startup scan:** make it multi-threaded (cold scan scales about 2.5× with 2 threads and is latency-bound), sorted/batched by directory, and compare against the DB with `(ino, size, mtime, ctime)` from the `statx` already in hand. Budget ≈ 20–40 s per 1M entries cold on this disk. Keep mounts blocked until it finishes (as §7.4 says); consider an incremental alternative for ≥ 3M entries (btrfs generation numbers or per-dir mtime sets) since the full scan thrashes if metadata does not fit in RAM.
8. **Capacity guidance (to add to the doc):** per cached entry ≈ 0.4–0.5 KB of btrfs metadata on disk (×2 with DUP) and ≈ 1.2 KB of reclaimable inode/dentry cache when scanned; never rely on `MemAvailable` when marks or leases pin inodes. At 3M entries expect > 3.5 GiB of cache for a full resident namespace, so 3M needs ≥ 8 GiB RAM or a smaller namespace (per-root policies, §10). Prefer `core.trustctime=false` and materialization in batches (≈ 15–60k entries/s).
